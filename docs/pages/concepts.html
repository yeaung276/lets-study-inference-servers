Concepts

Parallelism

Ranks

A large model is often too big or too slow for one GPU. So the inference engine starts one process per GPU, and the processes run the model together. To send data to each other, each process needs an address. That address is a number called its rank. Each process has two addresses: a global rank, unique across every process on every node, and a local rank, unique only within its own node.

Process groups

A process group is the set of ranks that work together for one purpose. One rank can belongs to several groups at once.

Ranks in a group talk through collective operations: steps that every rank in the group must join. One example is all-reduce, where every rank ends up with the sum of everyone's data. If one rank skips the step, the others wait forever.

Collective operations

MoE all-to-all

To understand all-to-all, we first need to understand expert parallelism (EP). In a MoE layer, each expert is an FFN. EP distributes these experts across ranks, where a rank can be a node or a GPU and can hold multiple experts. When a token's activation reaches the MoE layer, a router selects the most relevant experts, and the token vector is sent to the ranks that hold them.

The all-to-all operation enables this exchange of data. Because we don't know which experts will be chosen until the router sees the activation, every rank must be able to send data to every other rank, hence the first "all". After each expert computes its output, the result is sent back to the token's original rank, hence the second "all".

Scheduling

Zero-overhead scheduling (ZOS)

An inference engine generates text in decode steps: each step produces one new token for every running request. Each step needs both CPU and GPU work. The CPU schedules the step (picks the requests and builds their inputs) and later post-processes it (appends the new tokens, checks for stop tokens, sends outputs to clients). The GPU runs the forward pass and samples the next tokens.

Without ZOS, the two sides take turns, so every step the GPU sits idle while the CPU post-processes one step and schedules the next. Zero-overhead scheduling (ZOS) overlaps them: the CPU schedules step N+1 while the GPU still runs step N, and post-processes step N while the GPU runs step N+1. The GPU never waits for the CPU. The catch: step N+1 is built before the CPU has read step N's tokens, so the GPU fills them in itself.

When the length passes a multiple of 4, schedule gives the request a free slot: r1 has [3] at length 4 and [3, 9] at length 5. samplingHow to pick the request's next token: a temperature, or greedy (always the most likely token). Illustrative.
remapWith ZOS only. The request's row in the previous step's batch. Prep finds it by comparing the two batches. The GPU uses it to find the request's input token among the previous step's sampled token ids: on the GPU side, each D2D arrow reads the sampled row that remap names ("row 0").
inputWithout ZOS only, in place of remap. The request's input token id (the word under it is only for reading), which the CPU already has because it post-processed the previous step before scheduling this one. Prep adds it to the scheduled batch, and H2D copies it straight into input_ids; there is no D2D gather.
Sampled token idsThe token ids the latest sample picked, one row per request of that step's batch. They stay in GPU memory, where the next step's gather reads them, and are also copied to the pinned buffer (D2H).
Batch data (H2D)The scheduled batch's lengths, slots and remap, copied to the GPU by H2D, one row per request.
CUDA graphForward's kernels, recorded once with fixed GPU buffers as their inputs and output. Each step replays the recording, so forward always reads the same input buffers (the placeholders below) and writes the same output buffer. Forward reads the input placeholders and the earlier keys and values in the GPU memory slots, stores the input token's keys and values in the slots, and writes the output.
CUDA graph inputsThe graph's fixed input buffers, one row per request of the step that runs next. A row keeps its old value until this step's copy overwrites it. The step's inputs block fills them in three copies: H2D brings the batch data in, the metadata kernel writes pos and slots from it, and the gather (D2D) writes input_ids.
input_idsThe request's input token: the token the previous step sampled for it. The gather copies it from the sampled token ids, from the row remap names.
posWhere the input token sits in its request, counting from 0 (length − 1).
slots (graph input)The request's GPU memory slots, copied from the batch data, so forward knows where the request's keys and values live.
Output (hidden state)The graph's fixed output buffer: one hidden state per request, the model's final list of numbers for the input token. Sample turns it into a score for every possible next token and picks one.
eventA marker the CPU adds to the CUDA stream after each sample. "Wait for sample N" ends when the GPU reaches it.
