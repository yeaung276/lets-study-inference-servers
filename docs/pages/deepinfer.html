DeepInfer

How DeepSeek's inference engine is put together, from the system around it down to the parts that run every step.

Architectural overview

DeepInfer is the inference engine behind DeepSeek's production service, released as an offline engine for DeepSeek-V4.1-Flash. You give it prompts and SamplingParams, and it returns generated tokens. It started as a fork of vLLM and keeps that shape: a Python LLM wrapper, an LLMEngine that runs one scheduling step at a time, and a worker that runs the model on the GPU. The scheduler, block allocator and input preparation were moved to C++ (csrc/engine), and almost every kernel comes from DeepSeek's own libraries.

Three ideas explain most of the design:

  1. One engine per data-parallel (DP) rank. A launcher starts one process per DP rank. Each process has its own scheduler and KV cache, and serves its own requests. Ranks only meet inside the model (MoE expert all-to-all) and in a small vote that keeps every rank on the same step type (prefill or decode).
  2. The CPU never waits for the GPU. Under zero-overhead scheduling (ZOS), the CPU post-processes step N−1 and schedules step N+1 while the GPU runs step N. Decode steps replay captured CUDA graphs, and the hot path refuses any cuda synchronize.
  3. Production pieces stay outside. The load balancers, KV cache storage (3FS) and the prefill/decode split live outside this release. The engine still has the hooks for them (EngineType.PROMPT / COMPLETION, pe_do_save_kvcache).

Context diagram

C4 level 1 shows DeepInfer as one box, with the people and systems around it in a real deployment. It follows the reference architecture in DeepSeek's deployment Q&A. The story is simple: a user's request comes in as JSON, Recipe turns it into tokens, the request is routed to a DeepInfer engine, and the answer goes back the same way.

ComponentWhat it doesLinks toSource
◆ LLM entrypoint The public offline API. Tokenizes prompts, deep-copies SamplingParams per request, calls add_request, then loops step() until no request is left. When the loop ends it calls flush_inflight_reqs() to drain the last ZOS step, and can detokenize the results. Caller, LLMEngine entrypoints/llm.py
◆ LLMEngine Owns one DP rank. At startup it starts the workers, loads weights, measures free memory, allocates the KV cache and warms up or captures CUDA graphs. After that, each step() schedules a batch, clones or zeroes state for forked sequences, collects multimodal results and runs the worker. Its post_process callback turns sampled tokens into RequestOutputs and frees finished sequences. LLM entrypoint, Scheduler, Driver Worker, Multimodal processor, SO matcher builder, Stats logger engine/llm_engine.py, engine_type.py
◆ Scheduler (C++) Builds each step's batch. A two-round all-reduce vote decides prefill or decode for the whole DP group. Prefill chunks prompts within a token budget and a FLOPs budget (FlopsEstimator) and never cuts an image in half. Decode picks sequences last-come-first-served and preempts the one with the shortest output when blocks run out. It also sizes per-sequence draft lengths for speculative decoding. LLMEngine, BlockManager, peer DP ranks (vote) scheduler.hpp, flops_estimator.hpp, mtp_varlen.hpp
◆ BlockManager (C++) A free-list allocator with two instances: one hands out paged KV block ids, the other hands out per-sequence state slots (SWA window and compression state). Each request gets OK, LATER or NEVER. Scheduler; its ids index CacheEngine tensors block_manager.hpp
Sequence and output pools (C++) Sequence state, SequenceMetadata and RequestOutput object pools, output processing and sampler input prep, all exposed through pybind. Objects are released one step late (DeferredRelease) because the GPU may still be reading them. Scheduler, LLMEngine, ModelRunner sequence.hpp, process_output.hpp, prepare_sample.cpp
◆ Driver Worker The CP-rank-0 worker inside the engine process. execute_model_step runs in a fixed order: forward this step, post-process the previous step, sample this step, then post-process. Prefill steps post-process at once; ZOS decode steps defer it so it overlaps the next forward. It also forwards each call to the CP followers. LLMEngine (callbacks), ModelRunner, CP follower workers worker/worker.py, worker/base.py
◆ CP follower workers Started only when cp > 1, one process per extra CP rank. Each loops forever: receive (method, kwargs) from the driver, then run the same method on its own GPU. Driver Worker (shared-memory queue) worker/base.py, shm_broadcast.py
◆ ModelRunner Turns SequenceMetadata into InputMetadata tensors (in C++, with ZOS-aware variants), picks the CUDA graph for the batch size, then replays it (decode) or runs eagerly (prefill). It also prepares sampler inputs. At startup it profiles memory and records a decode latency curve that the scheduler uses. No cuda synchronize is allowed on this path. Driver Worker, DeepseekForCausalLM, Sampler model_runner.py, cuda_graph_runner.py, csrc/engine/input_metadata/
◆ CacheEngine Works out how many KV blocks fit after profiling, allocates them as raw uint8 buffers, and carves per-layer views from them: compressed KV and indexer KV (paged), plus SWA and compression state (one slot per sequence). DeepseekForCausalLM (read/write), BlockManager (ids), ModelRunner worker/cache_engine.py
◆ DeepseekForCausalLM The V4.1 model. Each decoder layer runs MLA attention (compressed KV, a sparse top-k indexer and a sliding window) and an MoE FFN, wrapped in mHC residual mixing. Some layers add Engram n-gram memory. The model also has a DSpark/DFlash draft head, YoCo prefill truncation and cross-layer KV sharing. The VL variant adds a ViT encoder. ModelRunner, CacheEngine, EPLB, kernel libraries, peer ranks (DeepEP) deepseek.py, decoder_layer.py, v4_modules/, mtp/dflash.py
◆ Sampler Applies temperature, top-k and top-p, and returns logprobs. It verifies draft tokens for speculative decoding and applies structured-output token masks. With a fixed seq_seed, sampling is deterministic. ModelRunner, SO matchers, DeepSelect layers/sampler.py, sampler_utils.py
◆ EPLB Expert-parallel load balancer. It counts tokens per expert over a window. At a set interval it recomputes which physical slot holds which expert, giving hot experts redundant copies, then moves the weights in place over NVLink symm_mem or NCCL P2P. MoE layers, EP peer ranks model_executor/eplb/
◆ Multimodal processor Forked processes turn image bytes into patches and put them in a shared-memory pool. Each step the engine collects the finished ones and marks those sequences ready to schedule. The ViT itself runs inside the model on the GPU. LLMEngine, Scheduler, DeepseekVL model ve/, deepseek_vl.py
◆ SO matcher builder A CPU-pinned thread pool that compiles regex, JSON-schema and EBNF grammars with xgrammar in the background. Each compiled matcher is attached to its sequence, and the sampler uses it to mask tokens. LLMEngine, Sampler structure_output/
Parallel state Creates every process group: world, DP, CP, EP, EP-in-DP and ENP, plus gloo CPU copies for the scheduler vote. It also creates the shared-memory queue used for CP broadcast and the symmetric buffers DeepEP uses. All distributed components parallel_state.py, userbuffer.py
HF loader Reads config, tokenizer and safetensors. Before loading, it checks shard integrity, that every parameter is covered, and that each quantized weight has its scale. ModelRunner (load_model), Hugging Face Hub hugging_face/, model_loader.py
deep_cluster / platform Detects NVIDIA or Ascend hardware from procfs and sysfs, binds processes to NUMA nodes and CPUs, and picks the TileLang backend (cuda or asc). LLMEngine, workers, kernels deep_cluster/, platform.py, npu_ops/
Stats logger / profiler Logs throughput, step time, MoE balance (moe_lb) and memory at intervals. An optional HTTP endpoint triggers torch profiling while the engine runs. LLMEngine stats_logger.py, profile_server.py

Request lifecycle

This table follows one request through a NORMAL engine, which does both prefill and decode, with zero-overhead scheduling on (the default). Steps 3–7 repeat until the request finishes.

#WhereWhat happens
1LLM entrypointThe prompt becomes int32 token ids. add_request creates a Sequence and puts it on the scheduler's waiting queue. If the request has images, the multimodal workers process them first. If it has so_args, a grammar compiles in the background.
2Scheduler: step typeEvery DP rank votes over an all-reduce. Prefill is tried every 70 decode steps if all ranks have prefill work, and every 100 if any rank does. A rank with nothing to do runs an empty placeholder step so the collectives stay in lockstep.
3Scheduler: batchPrefill takes prompts in FIFO order, cut into chunks by a token budget and a FLOPs budget, and reserves KV blocks and a state slot for each. Decode moves prefilled sequences into running, picks last-come-first-served, and preempts the shortest output when blocks run out.
4Driver Worker: forwardModelRunner builds InputMetadata in C++. Decode replays a CUDA graph; prefill runs eagerly. Inside the model, MoE tokens go to their experts and back through DeepEP.
5Driver Worker: previous stepWhile the GPU runs step N, the CPU finishes step N−1: it appends the tokens, checks stop conditions and builds RequestOutputs. This overlap is what "zero-overhead" means.
6SamplerSamples step N. With DSpark on, it checks the draft tokens, keeps the accepted prefix and sizes the next drafts from confidence. Structured-output masks apply here.
7EPLBRecords expert load. Every M steps it moves experts between GPUs.
8FinishWhen the request hits EOS, max_tokens or a stop condition, the scheduler frees its blocks and state slot (one step late). The entrypoint collects the outputs, drains the last step with flush_inflight_reqs(), and detokenizes.

Parallelism and processes

A launcher (examples/_launch.py) starts one process per DP rank on each node. World size is dp × cp, and EP groups are consecutive runs of ep_size ranks.

AxisWhat is splitCommunicationProduction guidance
DP (attention)Requests. Each rank has its own engine, scheduler and KV cache.Only the step-type vote (gloo CPU group under ZOS)Prefill DP2–8, decode DP64–128; #DP = #EP
EP (MoE)Routed experts, plus redundant copies of hot expertsDeepEP dispatch and combine (all-to-all over NVLink or RDMA); EPLB weight shufflePrefill uses the smallest EP that fits in HBM; decode uses "wide EP" (64–128)
CP (context)The tokens of one long prompt, split across GPUs in a balanced "mirror" layoutAll-gather of hidden states; driver-to-follower calls over a shared-memory queueSupported, but not used in production (up to 5% slower than DP)

KV cache and memory

V4.1 attention keeps two kinds of memory per layer. Paged stores grow with context length and are addressed by block ids. State stores are a fixed size per sequence and are addressed by a state slot. CacheEngine holds the tensors, and the C++ BlockManager hands out the ids.

StoreHoldsAddressed byNotes
ca_cacheCompressed attention KV (one entry per ratio tokens)Block id (paged)Data and scale per token: 288 B for per-16 FP4, 528 B for MXFP8
ica_cacheIndex-attention keys for sparse top-k block selectionBlock id (paged)Read by the MQA indexer to choose which blocks to attend
swa_cacheSliding-window attention KVState slotA ring of FP8 data (512 B) plus a UE8M0 scale (16 B) per token
ca_state / ica_stateCompressor and indexer state that is still accumulatingState slotFP32 ring; not written to disk
DFlash draft KVKV for the speculative draft headSeparate draft cacheFilled from target-layer features during the main forward

Glossary

TermMeaning in DeepInfer
ZOSZero-overhead scheduling: post-processing of decode step N−1 overlaps the forward of step N.
Engine typeNORMAL does prefill and decode; PROMPT does prefill only; COMPLETION does decode only. The last two are the hooks for P/D disaggregation.
MLAMulti-head latent attention: attention over a low-rank latent KV, here compressed further and read sparsely through a top-k indexer.
SWASliding-window attention; its KV is a fixed-size ring per sequence (a state slot), not paged blocks.
YoCo"You only cache once" layer split. Upper (consumer) layers reuse shared KV, which lets prefill truncate their work to a bounded suffix.
DSpark / DFlash / MTP / nextnSpeculative decoding: a draft head proposes up to nextn tokens, the main model verifies them, and a confidence model decides how many to draft per sequence.
mHCManifold-constrained hyper-connections: a residual stream widened hc_mult times, mixed before and after each sub-layer.
EngramHashed n-gram embedding tables added to the hidden state, sharded across ranks by vocabulary (ENP).
EPLBExpert-parallel load balancer: redundant expert copies placed according to measured load.
Placeholder stepAn empty step a rank runs so that collectives stay in sync with ranks that have real work.
